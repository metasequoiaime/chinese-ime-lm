# 选词模型设计（草案）

状态：方向已定，正在做 P0 延迟实测。

## 为什么要换结构

2.0 的实验（2026-10-31）给出三个结论：

- 换语料有效：24.9M 只换成保留标点、整篇连续的语料，dev-select 从 1237 到 1300（82.5% → 86.7%），参数不变。
- 蒸馏无效：在语言模型上加列表损失，只学标准答案和学 9B 老师的打分两组，都没有超过起点（1300 / 1500）。学习率 1e-4 把模型学坏，3e-5 学不动。
- 知意强在结构：它是编码器加选词头，读前文、敲的拼音和整页候选，一次前向给整页打分，int8 84–92 MB，CPU 4 线程 5–10 ms。我们的模型是逐字语言模型，看不到拼音，选词只是借用下一个字的概率。

所以要训的不是一个更大的语言模型，而是一个以"选对候选"为目标、读得到拼音的模型。老师的 10 万份打分和 5 亿字语料都能直接用上。

## 约束

- **延迟**：按键路径 p95 不超过 10 ms（当前 4.25M 是 8.61 ms，帧预算 16 ms），桌面 M4 Pro 单次决策量。移动端另测，标准不放宽。
- **体积可以大**：桌面可以到 100 MB 级。移动端键盘扩展的进程预算是几十 MB，单独定。
- **运行时**：参考实现是纯 Rust、无 unsafe、无数值库依赖，单核约 12.5 GMAC/s，已经是算力打满的（`docs/measurements.md`「推理」）。选词模型改用 ONNX Runtime（见「已定」）。
- **MSIME 接入**：`rerank_pick` 现在只收到前文和候选文字，拿不到拼音（`OrderRow` 只有 `text`、`source`、`answers_key`、`corrected`）。要把组字的拼音一起传进来，engine、input-runtime、engine-wasm 三处调用都要改。

## 延迟预算决定了什么

10 ms × 12.5 GMAC/s ≈ 1.25 亿次乘加。一个 token 的代价约等于非嵌入参数量（嵌入是查表，不花算力）。

- 现在的 4.25M（6 层、宽 192、词表 8192）每个 token 约 420 万次乘加，其中约 160 万花在输出头上：每个位置都要对 8192 个字算一遍概率。
- 选词模型不需要这个头，只在每个候选末尾算一个分数。同样的每 token 代价，可以全部给到层上。
- 嵌入表不花算力。体积预算主要应该花在这里：更大的字表、拼音音节表、词级嵌入。这正是"可以大、延迟不能高"能同时成立的地方。

结论：按键路径上可以加的是"体积"，不是"每个 token 的算力"。每 token 算力最多和现在的 4.25M 持平，除非运行时变快（见下面的决策 2）。

## 结构

一个带条件的解码器，不是双向编码器，为的是保住现有运行时的两笔最大优化：

```
[前文 ≤ 64 字] [SEP] [敲的字母] [SEP] 候选字1 候选字2 ... [END] → 分数
```

- **前文**：上屏时算一次并缓存，不在按键路径上（和现在的前缀缓存相同）。
- **敲的字母**：a–z 和分隔符，作为 token 输入。直接用字母，不依赖音节切分；纠错行、模糊音也能处理。
- **候选**：每条候选因果地读前文、字母和自己前面的字，候选之间互不可见。这样跨按键按位置续算照样可用（实测每次按键 61% 的字符可以复用），也可以把候选分到多个线程上并行。
- **打分**：候选末尾 `[END]` 位置接一个线性层出一个标量。整页取 softmax，用列表损失训练。
- **嵌入**：字嵌入 + 字母嵌入 + 位置嵌入 + 段落类型嵌入（前文 / 字母 / 候选）。初版不做词级嵌入，留作体积预算的第一个加法。

## 训练数据

- **题目**：`build_cases.py` 已经能从语料造出带前文的题（拼音、候选池、标准答案），并排除评测集的重叠。从 2.0 语料造几百万道。
- **标签**：标准答案做交叉熵；有老师分数的 10 万道加 KL 蒸馏。在这个结构上，蒸馏的目标和模型的输出对得上。
- **初始化**：字嵌入和前几层可以从 2.0 的 24.9M 或 4.25M 预训练拷过来，省下从零学语言的时间。

## 已定（2026-10-31）

1. **延迟预算**：按键路径 p95 ≤ 10 ms，桌面和移动端同一标准。
2. **运行时**：用 ONNX Runtime。参考实现单线程已经算力打满，要让每个 token 的算力超过现在的 4.25M，只能换运行时。代价要接受两点：MSIME 多一个原生依赖（Rust 侧的 crate 和版本在 P4 加之前单独确认），以及 engine-wasm 用不了它，网页版继续用现在的语言模型重排。
2b. **延迟是硬约束，可以用多线程**（2026-10-31 补充）：看的是尾部，不只是 p95，p99 和最慢一次同样要看，偶尔卡一下也算高延迟。P0 同时量 1、2、4 线程。手机单核比 M4 Pro 慢，中低端安卓可能慢 2–3 倍，所以桌面上暂定 p99 ≤ 4 ms 才算过关，给手机留余量，最后以真机实测为准。
3. **平台**：桌面和移动端一起做。移动端的硬约束是键盘扩展几十 MB 的进程内存，P0 的线程档见 2b。体积预算按移动端定，桌面档可以另出一个更大的版本。

## 还没落实的风险

- MSIME 已经在六个平台上带着 ONNX Runtime：本地语音识别用的 sherpa-onnx 1.13.8（`resources/voice-runtime.lock.json`）自带它，HarmonyOS 也有（ohpm 的 `sherpa_onnx` 包）。所以 HarmonyOS 能跑 ONNX Runtime 已有先例。但它不能直接复用：苹果平台上 ONNX Runtime 静态链接在 sherpa-onnx 的库里面，macOS 的语音识别还跑在单独的进程里（`msime-voice-local`）。选词模型要在输入法进程里跑，得自己带一份 ONNX Runtime，安装包会变大，移动端键盘扩展的内存也要把它算进去。
- 前文缓存和跨按键续算要靠把每层的 K/V 作为图的输入输出来实现，ORT 能做，但 P0 先只量"前文已缓存、候选每次重算"的保守口径。

## 聊天上文：一个人前几条消息当上文（2026-11-03 至 11-04）

**问题。** 输入法在聊天里看到的上文，是同一个人前面发出的几条消息，中间隔着换行。按键模型（`lm-8x448-c3`、`phone-6x256`）训练时，LCCC 的题只拿同一轮里前面的话当上文，从没见过这种形状。到了 MSIME 的单人聊天评测里，它在上文是「妈」的时候，仍然把「下个月是爸的生日」打成「十八」，把「你和爸」打成「喝吧」；一条消息里的「他」打错了，后面几条的「她」也跟着错。9B 老师在 2.0 选错的 55 句聊天里能选对 39 句，所以这里是模型判断的问题，可以靠蒸馏解决。

**第一轮：LCCC 造题，不迁移。** `neural/teacher/build_chat_cases.py` 从 LCCC 对话里给第 t 轮找同一个说话人的第 t−2、t−4… 轮，用换行连起来当上文，造出 3 万句训练题、1000 句开发题。9B 老师给 19,562 个池打分后，从发布的模型接着训（`--phase pools --lm-only`）。LCCC 聊天开发集从 86.6% 涨到 90.0%，但放进 MSIME 引擎（`convert_eval --autocorrect --sentence-pool 32`）测单人聊天集只净多对 2 段（330 段）。LCCC 是社交网站上的开放对话，同一个人的前后几轮很少接着说同一件事，不像一个人给家人、同事连发消息。

**第二轮：合成的单人连发聊天。** `neural/teacher/gen_chat.py` 让 DeepSeek 的 `deepseek-v4-pro` 写只有发送方一侧的聊天，每段 8 到 14 条，发送人、聊天对象和话题按种子组合（20 种发送人 × 18 种对象 × 各自的话题），共得到 1,483 段。DeepSeek 的使用条款把输出归用户，并允许用来训练其他模型（第 4.2 节，2026-11-03 核对）。`neural/teacher/build_synth_cases.py` 让每条消息拿同一段里前面的消息当上文，整段对话按哈希分进开发集或训练集，排除所有评测集的句子和 8 字片段（含 MSIME 的 typing-chat-v1）。用前 1,352 段造出两批题，MSIME 引擎（c70b16174f）录出候选池，9B 老师打分 39,410 个训练池。9B 老师在合成开发集上对 95.5%，发布的 8×448 只有 84.2%，差距主要在词级题。

**通用能力的代价，以及怎么拿回来。** 只在聊天池上继续训，ctx-v1 有上文会掉几个点（`evaluate.py` 的口径）：8×448 从 91.8% 到 91.4%（配对检验 p = 0.03），6×256 从 90.1% 到 89.7%，跌破 90% 的底线。混进 2 万道通用池一起训没有用；训练时让语料窗口去拟合起点模型自己的分布（KL 到起点）更差（6×256 有上文 89.1%）。最后用的是权重插值 `neural/choice/interpolate.py`：8×448 取新权重七成，6×256 取五成。6×256 取七成时，在导出的 `lm_step.ort` 上量 ctx-v1 有上文是 4919 / 5468（89.96%），差 3 条够不到底线，所以退到五成。

**结果（2026-11-04）。** 8×448 是 `final-8x448-mix0.7`，6×256 是 `final-6x256-mix0.5`。MSIME 的三行用同一套引擎（c70b16174f）和资源，开纠错，整句池 32 条；ctx-v1 两行用 `neural/choice/score_ort.py` 在导出的 `lm_step.ort` 本身上量（发布版一列与 rerank-v1 的说明逐条相同）：

| | 8×448 发布版 | 8×448 新 | 6×256 发布版 | 6×256 新 |
|---|---|---|---|---|
| MSIME 带上文的单人聊天（330 段） | 80.6% | 83.3%（+11 / −2，p = 0.02） | 83.3% | 85.5%（+9 / −2，p = 0.07） |
| MSIME 无上文的聊天（330 段） | 80.0% | 82.7%（+11 / −2，p = 0.02） | 82.7% | 84.8%（+8 / −1，p = 0.04） |
| MSIME sentences 四套（1,580 句） | 87.8% | 87.8%（+13 / −13） | 84.5% | 83.8%（+16 / −27，p = 0.13） |
| ctx-v1 有上文（5,468 条，底线 90%） | 91.9% | 91.4% | 90.4% | 90.1% |
| ctx-v1 无上文（849 条，底线 80%） | 82.7% | 82.7% | 83.0% | 83.0% |

结构没变，按键延迟也没变：`rerank_latency` 在 M4 Pro 上逐键成对测量（单人聊天 test 集，开纠错，4,902 次按键，各两遍；6×256 量的是取七成的那一版，结构与权重布局相同），6×256 整句池 32 条时，带模型 p95 3.29–3.37 ms 对 3.33 ms，p99 4.92–5.02 ms 对 4.89–4.98 ms；8×448 整句池 9 条时，p95 6.81–6.84 ms 对 6.70–6.78 ms。

**没解决的。** 合成开发集的整句题里，有 43% 的正确答案不在引擎给出的候选里，这部分只能改候选生成，重排模型帮不上。没有上文时的「他/她」本来就分不出，新旧模型各有翻转。
