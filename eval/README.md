# 评测集

把「某个改动好不好」从意见变成数字。两条路线——n-gram 与神经模型——用同一把尺子，所以可以直接比较。

两个文件测的**不是一回事**，分开读。

## `quanpin-words-v1.tsv` — 25,119 条词级

从 [Windows-classic-samples](https://github.com/microsoft/Windows-classic-samples) 的全拼示例词库（MIT）固化而来。

生成时丢弃 27,561 条单字和 1,955 条截断条目，无解析失败。截断过滤用的判据是「拼音串能否恰好切成与答案字数相同的音节数」，而不是长度阈值——该格式在 12 字符处截断，但 `chulufengma`、`shumenshul` 这类更短的串同样被砍，长度阈值漏得掉。

**它测的是词典命中与排序，不是整句能力。** 正确答案几乎全部来自词典的整键命中，词图一次都没有贡献过。想测整句能力，用下面那个集。

**不要拿你自己的词库出题。** 那就是解码器查的那张表，等于让系统考自己；而短词的排序实现往往就是按词频降序，拿词频当金标准是在考数据库。

## `sentences-v1.tsv` — 60 条整句，手写

整句语料不像词库那样现成，所以这部分是手写的。金标准是「母语者在该拼音串下唯一自然的写法」；拼音本身就有两种同样自然写法的句子一律不收——评测集不能既诚实又有歧义。

**n=60 的统计分辨率：单臂比例的 95% 置信半宽约 ±13 个百分点。** 聚合数字的小幅变动不构成证据。两次运行要**逐条比对每个答案的排名**，而不是对着汇总值做减法。

标签分布：`function-word` 10、`seg-ambiguity` 12、`homophone` 12、`number-measure` 6、`name-place` 6、`long-sentence` 8、`short-phrase` 6。人名一律是常见姓 + 通用名，不含真实个人信息。

## 格式

制表符分隔，`#` 开头为注释。

```
id	input	gold	syllables	tags
s-001	wojintianqushangban	我今天去上班	6	function-word
```

## 怎么用

**神经模型**（本仓库内）：先让你的引擎把候选列表录成 JSONL，每行 `{"input":…, "gold":…, "context":…, "candidates":[{"text":…,"source":…}]}`，再打分：

```sh
python neural/rerank_eval.py --model dist/model.safetensors --cases dumps/sentences.jsonl
```

参考实现里还有两个：`reference/examples/replay.rs` 回放同样的 JSONL（用来交叉验证两种实现是否一致），`reference/examples/hybrid.rs` 扫描组合权重。

**把候选录出来，是每个输入法自己的事。** 那一步要驱动真实引擎和真实词库，本仓库不假设你的引擎长什么样。

## 分来源报告，不要只报一个数

候选要带上来源，并**按来源分桶报告**。这不是形式要求——一个整体提升的数字可以掩盖着词典桶的回退。[`docs/measurements.md`](../docs/measurements.md) 里的实测就是这个形状：重排在解码器拼装的候选上有用，在词典整键命中上有害。

来源的编号是各家引擎自己的事。这两个评测集里的 `source` 字段沿用了它们出身的那个引擎的编号（`Database` 为 0、`UserDatabase` 为 1、词图为 8、回退为 9）；换成你的引擎时，只要保证「词典整键命中」和「解码器拼装」这两类能分开即可。

## 两个会悄悄毁掉测量的陷阱

**只有等长候选可比。** 对数概率求和时字数越少值越大，混长度的列表里最短的永远排第一。用这种方式测会显示模型在破坏准确率，而同一份权重在等长集合上是提升的。

**评测能用的门控，运行时用不了。** 评测知道正确答案，可以按它的长度过滤；输入法不知道。用你真正会发布的判据去测，否则数字比产品好看。

## 已知测不到的东西

词表覆盖（词级集的答案 99.94% 本来就在词典里）、用户学习与调频（评测必须关掉，否则前一条会污染后一条）、双拼、九宫格、语言模型困惑度（本仓库不分发语料）。
