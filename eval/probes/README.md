# 探针

这里的文件**不是评测集**,别拿它们的数字当结论。

`eval/` 下那两个评测集衡量的是已经存在的行为。探针不同:它回答"如果我们要做某个还不存在的功能,拦路的是哪一层",答案只需要定性。用例是手写的,候选列表是**假设引擎会产出的样子**,不是从真实运行时录出来的——这一点与 [`eval/README.md`](../README.md) 里说的"把候选录出来是每个输入法自己的事"正好相反,所以探针不能替代那件事。

跑法和评测集一样,用 `replay.rs`:

```sh
cd reference
cargo run --release --example replay -- ../dist/sentence-model.safetensors \
  ../eval/probes/typo-correction-hypothetical-v1.jsonl
```

## `typo-correction-hypothetical-v1.jsonl`

问题是:**要给输入法加拼音纠错,模型这一侧要不要重训。**

模型词表里一个拼音字母都没有(8192 / 12288 个 token 除三个保留位外全是单个汉字),所以它不可能"纠正拼音"。它只能在引擎造出来的汉字候选里挑。于是真正该问的是:引擎把纠错后的读法造进候选之后,现在这份权重能不能挑对。

16 条,分四组,各回答一个不同的问题:

| 组 | 条数 | 构造 | 问什么 | 4.25M | 24.9M |
|---|---|---|---|---|---|
| A | 8 | 纠错后的候选与引擎首选等长,无词典证据 | 模型挑得对吗 | 6 / 8 | 7 / 8 |
| B | 3 | 正确读法与首选**字数不同**(`xian` → 现 / 西安) | 门控让模型看到它吗 | **3 / 3** | **3 / 3** |
| C | 2 | 首选是词典命中,且引擎**为它背书** | 该不该插手 | 0 / 2 | 0 / 2 |
| D | 3 | 同 C,但引擎**声明不背书**(它知道自己纠了键) | 声明之后模型动手吗 | 2 / 3 | 2 / 3 |

**C 组的 0 / 2 是正确行为,不是失败。** 引擎说这条词典命中值得采信,模型就该让位——这是 2052 例实测支撑的策略。D 组是同一份候选、同一个上下文,只把那句声明改掉,模型立刻动手并挑对。两组放在一起说明的是:**这个决定在引擎手里,不在权重里。**

**引擎首选在每一条里都是错的,这是构造出来的。** 所以 `replay.rs` 报的 `engine 0.000` 和那个 `+0.545` 的 delta **不是准确率提升**,只是"13 条里模型挑对了几条"。把它当成模型收益去引用是错的。

**13 条什么都证明不了(定量上)。** [`docs/measurements.md`](../../docs/measurements.md#52-条上没有任何一对模型达到显著) 里算过:按实测的分歧率,要检出 1 到 2pp 的差别需要一千到近万条用例。这里要的不是 pp,是"A 组大体能挑对、B 和 C 组全军覆没"这种量级的定性差别——这个 13 条看得出来。

**收录规则同样适用。** 拼音上有两种同样自然写法的句子不收,否则失败的是出题人不是模型。第一版里有一条 `jianyi` → 讲义,上下文是"老师发的",但"老师发的建议"在中文里一样成立,已经换成搭配唯一的 `yinxiang` → 影响("产生了很大的影响"成立,"产生了很大的印象"不成立)。

### 结论

**模型这一侧不用重训。** A 组 6 / 8 与 7 / 8,引擎首选每条都是错的,模型自己纠回来了。

**B 组暴露了一个真缺陷,已经修了。** 第一次跑时两个模型 0 / 3,原因不是挑错,是**根本没参与比较**:`best_where` 当时只比较与首选等长的候选,而 `xian` 读成"西安"是两个字、首选"现"是一个字。但[「只有覆盖整个键的候选之间才可比」](../../docs/measurements.md#两个会悄悄毁掉你测量结果的陷阱)这条原则从来没说过"等长"——字数只是它在"一个键一种切分"前提下的代理,而纠错和切分歧义正好破坏那个前提。改成由调用方声明 `answers_key` 之后 3 / 3。

顺带回答了一个当时不确定的问题:按字数归一的均值**跨长度也站得住**。担心过一个字的候选会因为均值只摊到一项而占便宜,这三条上没有发生。

**C 与 D 组说明剩下的决定在引擎手里。** 门控本身是对的——2052 例词典命中上,覆盖它在任何阈值下都掉分。要修的是那条规则的**前提**:"词典答完整个键说明它带着语料词频",而用户打错拼音时,词典命中的是**用户没想打的那个键**,词频成了另一个词的证据。所以 `trusted_dictionary_hit` 问的不是"词典匹配上了吗",而是"这条命中值得让模型让位吗"。引擎既然知道自己纠了键,就该对未纠正读法的命中回答"不值得"。C 组答"值得"→ 模型让位(正确);D 组答"不值得"→ 模型动手并挑对。**一行声明的差别,跟权重无关。**

### 仍然挑错的那条

`gongsi` → 公式 在 A、C、D 三组里对两个模型都没挑对,上下文是"这个数学"。"这个数学公式"对人来说没有歧义,所以这条是模型自己的失误,不是门控或可比性的问题——大概是"公司"的语料频率压过了上下文。上下文只有四个字也可能不够。这条留着,它是少数几条能反映模型真实短板的用例。
